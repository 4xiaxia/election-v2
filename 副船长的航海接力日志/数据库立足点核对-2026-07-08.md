# 数据库立足点核对 - 2026-07-08

> 目的：从 live schema 往上核对当前 UI/业务设计有没有数据库落脚点。结论分为：已对上、半对上、未找到家。

## 验证方式

- 已在 `koaLite` 下执行 `npm ci --omit=dev --ignore-scripts` 恢复只读核对所需依赖；未启动服务，未写数据库。
- 已跑 live schema 只读脚本：`SHOW TABLES`、`SHOW COLUMNS`、关键表 `COUNT(*)`、抽样解析 `elections.content`。
- live DB 当前关键表：`users/villages/elections/positions/materials/candidates/notices/notifications/message_reads/election_voters/logs`。
- live DB 当前缺表：`roster`。

## 小 mini 核对结论

| 小 mini | 观察重点 | 结论 |
|---|---|---|
| 结构官 | 漏斗链路是否能从表走通 | 主链已成立：`villages -> elections -> timeline/positions -> materials/notices/candidates`。不是多商户，仍是分级过滤。 |
| 字段官 | 设计字段是否有落脚点 | 大部分有家；最大缺口是 `roster`、短信通道配置、`notice-v2/list` 的 `stageKey` 后端筛选。 |
| UI 官 | 页面功能是否超出数据库 | 母版主体表基本可落；公告列一对多可落；花名册和短信配置 UI 目前超前于数据库。 |
| 接力官 | 下一刀怎么不乱 | 先补“半对上/没家”的最小承接，不要重建已有主表。 |

## 已对上：有明确数据库落脚点

| 设计/功能 | 数据库立足点 | 对应情况 | 备注 |
|---|---|---|---|
| 登录手机号、角色、子管理归属地 | `users.phone/role/village_id` | 已对上 | 后台管理员以手机号为登录名，子管理靠 `village_id` 锁当前归属地。 |
| 村/社区归属地 | `villages.id/name/type/street/status` | 已对上 | live DB `villages` 当前 124 条；甲方 122 名单仍需另核，不影响结构。 |
| 超管外层列表，下钻复用子管理 | `villages` + `elections.village_id` | 已对上 | 不需要多商户表；按分级过滤即可。 |
| 母版选举活动 | `elections.id/village_id/name/election_type/election_method/session_no/content/status/approval_status` | 已对上 | 一场选举活动就是一个大母版和存档单位。 |
| 选举方式关联归属地 | `villages.type` + `elections.election_method` | 已对上 | 村固定直选；社区通过 `election_method` 区分直选/户代表/居民代表。 |
| 母版阶段表主体 | `elections.content` JSON | 已对上但形状需统一 | live sample 是 `content.timeline[]`，含 `stageKey/stageName/startDate/endDate/days/work/noticeNos/materialNos/materials/stageStatus`。 |
| 阶段多条子公告 | `notices.election_id/stage_key/notice_no/template_key/title/content/status` | 已对上 | live DB 里同阶段已有多条公告，例如 `S1` 有 3 条、`S9` 有 6 条。 |
| 阶段归档材料 | `materials.scope=archive/stage_key/material_no/file_url/election_id` | 已对上 | `position_id/applicant_phone` live schema 已允许为空，适合阶段归档。 |
| 候选报名材料 | `materials.scope=candidate/election_id/position_id/applicant_phone/items/status/candidate_id` | 已对上 | 审核通过后回填 `candidate_id`，和候选人血缘闭环一致。 |
| 岗位管理 | `positions.election_id/name/quota/post_category/can_self_recommend/on_ballot/produce_way/post_status/incumbent/incumbent_phone/is_reelection` | 已对上 | live schema 已比初始 SQL 丰富，能承接岗位状态和产生方式。 |
| 候选人管理 | `candidates.election_id/position_id/phone/name/source/recommend_type/status/elected/votes/material_id` | 已对上 | 可承接材料审核通过 + 后台导入两来源。 |
| 通知/站内信/红点 | `notifications` + `message_reads` | 已对上 | `notifications.target_phones/user_id/target_role/target_village/scheduled_at/status`，`message_reads` 记录已读。 |
| 选民登记 | `election_voters.election_id/village_id/user_id/phone/name/status/register_source` | 已对上 | `users` 不是选民登记，`election_voters` 才是某届参与关系。 |
| 操作/审核/登录日志 | `logs.kind/actor_id/module/action/detail` | 已对上 | 表存在但当前 count=0，后续要看接口是否写入。 |

## 半对上：有家，但还要补字段/API/形状

| 设计/功能 | 现有立足点 | 缺口 | 下一刀建议 |
|---|---|---|---|
| `templateKey + stages[]` 模板化母版 | `elections.content.timeline[]` | live sample 没有 `templateKey`，字段名是 `timeline` 不是新稿里的 `stages`。 | 不新建表；统一 JSON 合同：保留兼容 `timeline[]`，新增 `templateKey` 或 `timelineTemplateKey`。 |
| 母版表公告弹窗按阶段查 | `notices.stage_key` | `notice-v2/list` 目前只筛 `electionId/type/status/title`，没有后端 `stageKey` 查询。 | 给 `notice-v2/list` 补 `stageKey` 参数；前端可临时按 `electionId` 拉后本地筛。 |
| 下载资源/模板文件 | `elections.content.timeline[].materials`、`admin/src/data/stageTemplates.ts` | 模板资源多在 JSON/静态表里；若要后台管理模板文件，没有独立资源表。 | 一期先不加表；母版 JSON 保存模板文件名，上传归档仍走 `materials.scope=archive`。 |
| 通知弹窗的“预告通知/消息通知/逾期提示” | `notifications.type/send_mode/scheduled_at` | 字段能放，但枚举和 UI 映射未完全压实。 | 在通知模块固定 type 枚举，不新建表。 |
| 日程日历 | `elections.content.timeline[]` | 当前 dashboard 还存在旧 11 阶段兜底；新设计是按模板阶段动态。 | 施工时从当前母活动 `timeline/templateKey` 生成日程，不手搓固定阶段。 |
| 选举提案审批 | 现在页面走 `materials.scope=proposal` | 这不是干净主线：`materials` 是某场选举下的材料，提案阶段可能还没有 `election_id`。 | 先决定是否一期范围；若保留，应补 `election_proposals` 表或明确用 `materials.scope=proposal` 的约束。 |
| 短信通知发送 | `notifications.target_phones` | 只能记录目标手机号和通知内容；真正短信通道配置没落库。 | 短信通道配置单独补最小 `settings`/`system_configs` 表或保持“配置未落库、仅占位”。 |

## 未找到家：当前 live DB 没有正式表/字段

| 设计/功能 | 当前状态 | 风险 | 建议 |
|---|---|---|---|
| 花名册/在职干部 roster | live DB 无 `roster` 表 | 岗位详情“在岗”如果直接用 `positions.incumbent`，只能放一个现任人，无法承接届次、任期、简介、手机号和历史在任名册。 | 按已定最小字段新增 `roster`：`id/village_id/session_no/year_start/year_end/post/name/phone/intro/status/created_by/created_at/updated_at`。 |
| 短信服务商通道配置 | `admin/src/views/settings/index.vue` 有 UI，live DB 无配置表 | AccessKey/签名/模板 Code 没持久化位置；不能宣称短信可配置。 | 新增 `system_configs` 或 `sms_channels` 最小表；敏感值必须环境变量或加密存储，不能写明文。 |
| 定时通知执行器 | `notifications.scheduled_at/status` 有字段 | 字段能排程，但未核到后台任务扫描发送。 | 一期可先标“记录待发送”；真正自动发送需另补 job/cron。 |
| 母版模板库表 | 当前模板在 HTML/静态 TS/JSON 中 | 不影响一期运行，但后台无法维护模板库。 | 一期不加表；模板作为代码配置，客户填完后的结果落 `elections.content`。 |

## 本轮结论

1. 主流程不是空中楼阁：归属地、母活动、阶段、公告、材料、岗位、候选人、通知、选民登记都有数据库根。
2. 最该先补的不是重建系统，而是补最小缺口：`roster` 表、`notice-v2/list stageKey` 查询、timeline JSON 合同统一、短信通道配置边界。
3. 已有的 `materials/notices/notifications/candidates` 不要删重做；按现有字段补强即可。
