系统施工导览：业务漏斗 × 侧边栏目录 × 数据库字段

给第一次接手的人看的总入口：先看谁决定谁，再看页面怎么跳，最后看字段挂哪里。所有页面都从同一条母活动链路往下走。

ID: system-global-funnel-001

1. 业务漏斗：谁在谁前面

归属地villages.id/type/name 决定这是村还是社区；子管理登录后锁定一个归属地。
母活动elections.id/village_id/session_no 决定一届换届；所有岗位、材料、公告、候选人都挂它。
时间轴elections.content.timeline 决定 11 个阶段；日历、公告阶段、归档材料都读它。
岗位positions.election_id/name/quota 决定主任/副主任/委员；同岗位不同届次不能混。
材料与候选人materials.scope=candidate 审核通过后生成/关联 candidates；scope=archive 只归档。
📌 真相边界 · ID: system-truth-order-001：页面只能投影这条链，不能把日期、岗位、材料、候选人做成各自一套真相。

2. 侧边栏目录：每个菜单吃哪层

村居管理维护 villages；它在最前面，决定后面列表默认范围。
选举活动管理维护 elections 和母版详情 /election/:id；阶段表、公告编辑、归档入口都从这里进。
岗位管理维护 positions；必须先选母活动，再看岗位需求、在岗干部、岗位状态。
材料提交管理吃 materials.scope=candidate；筛选顺序是归属地 → 母活动 → 岗位 → 参选形式。
候选人管理吃 candidates；来源是材料审核通过 + 后台导入，按同一岗位下钻。
审核/通知/归档审核改 materials/candidates.status；通知写 notifications；归档只看 materials.scope=archive。
🔌 侧边栏锚点 · ID: system-sidebar-route-map-001：菜单不是平铺功能，都是同一漏斗不同层的入口。

3. 字段决定链：谁决定谁

users.village_id决定子管理默认归属地；超级管理不绑定，先看外层列表再下钻。
villages.type决定选举方式集合：村委会固定村民直接选举；社区可直选/户代表/居民代表。
elections.id决定所有业务归属，是岗位、材料、候选人、公告、选民登记的主锚。
timeline[].stageKey决定日程、子公告、阶段归档材料的位置；跳步只能空着或标跳过。
positions.id决定报名材料和候选人属于哪个岗位；岗位说明/下载资源也必须带它。
roster.post决定岗位详情“在岗”卡片展示谁；匹配 post=positions.name，只做最小花名册。
materials.candidate_id决定报名材料与候选人的血缘；只有审核通过才回填，归档材料永不生成候选人。
💾 字段漏斗锚点 · ID: system-field-decision-chain-001：先有范围，再有母活动，再有阶段/岗位，最后才有材料、候选人、通知和归档。

🔀 岗位状态弹层路由 · ID: position-status-modal-route-001
岗位状态不是纯 UI 样式；不同状态点击进入详情，弹层内容不同，后续关联模块也不同。
在岗 → 花名册在任干部；竞选报名 → 公告+材料提交管理；提名公示 → 子公告+入围候选人；正式候选人公示 → 候选人管理；竞选中/投票中 → 线下进度投影；审核中 → 材料/候选人审核；结果公示 → 候选人结果回填。
