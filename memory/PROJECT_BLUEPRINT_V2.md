## 【根层】- 项目基础

### 项目目标与核心问题域
- **项目目标**：构建一套服务于莆田市城厢区（下辖 93 个村委会、29 个社区居委会，共 122 个单位）的一站式村居两委换届选举管理系统（election-v2）。以极低的预算和极高的人文关怀，服务基层选举经办、审核、运营和普通村民，确保换届流程“合法留痕、简单好用、防呆防错”。
- **核心问题域**：
  - **法定复杂性与基层的矛盾**：我国村委/居委会选举法条极其严苛（村委会只能全民直选，居委会支持三选一）。基层干部文化水平不一、操作极易违法或漏填。
  - **极低预算与开发成本的落差**：预算有限，不容许从零手搓多套庞杂的复杂逻辑或复杂的权限树。
  - **多源数据断链隐患**：活动时间、岗位要求、候选人审批和材料归档等环节，由于历史 Agent 缺乏大局观导致数据零散并轨，存在极易数据断链、局部成功全局失败的隐患。

### 关键概念与定义
1. **换届大母版（Mother Template）**：整个选举活动的唯一“太阳”和生命之源。本质是一个分阶段的、预设官方标准答案、但可弹性增删编辑的“填空套题”。一个活动一行母版，时间轴一填，全系统日历、岗位、材料、公告、归档全部自动映射。
2. **血缘翻转（Bloodline Inversion）**：传统的系统设计是先创建候选人再配材料；本系统彻底反向操作——村民在小程序端提交报名材料，后台审核通过的一瞬间，事务内自动生成候选人记录（`source='material'`）并回填 `candidate_id` 建立双向血缘。
3. **两套法定分岔**：
   - **村委会（行政村）**：班子 3~7 人（单数），选举方式**强锁死**为“全体村民直选”（不能用别的方式），允许不设副主任。
   - **居委会（社区）**：班子 5~9 人（单数），选举方式支持“全体居民直选/户代表选举/居民代表投票”三选一，必须设置副主任。

### 术语表
| 术语 | 英文对照 | 定义/解释 |
|---|---|---|

| **子管理** | `sub_admin` | 村子视角的管理员统称（包括经办、运营编辑、审核等角色），均属于村长权限的子集。 |

## 【主干层】- 工程骨架

### 架构分层
系统采用极致的前后端分离及单主源数据投影架构：
- **表示层 (UI Layer)**：`isdream-vue-admin` (Vue 3 + TS + Vite + ElementPlus)。
  - 全局样式真相源：`shared.css`，收口定义 `--red: #B22222`、`--gold: #C8A45C`、`--bg-page: #FAF8F5` 等视觉变量。
  - 组件小纸条（Component Sticker）心智：在页面中直接写清晰的组件功能纸条，由前端直接秒套。
- **控制层/外壳层 (Console Layer)**：唯一外壳 `页面-总台.html`，维护 9 项侧边栏菜单（支持 Iframe Embedded 内联与 Hash 路由）。
- **业务逻辑层 (API Layer)**：基于 `koaLite`。
  - 核心模块：`election-v2.js`（母版）, `position-v2.js`（岗位算法）, `candidate-v2.js`（漏斗机制）, `material-v2.js`（血缘逻辑）。
  - 安全隔离：`villageScope.js`，通过行级 `village_id` 在中间件自动实现子管理级别数据拦截与超管全局穿透。
- **数据层 (Data Layer)**：MySQL。10 张核心关系表，核心实体以大母版 `elections.id` 强并轨。

### 模块依赖关系
```
       [ 页面-总台 (外壳框架) ]
                  │ (Iframe 内联 / Hash 路由)
       ┌──────────┴──────────┐
[ 首页工作台 ]           [ 换届活动大母版 ] ───────┐
  (日历+通知铃)               │                   │ (主表)
                           ▼                   │
                     [ 岗位管理 ]               │ (映射/生成)
                           ▼                   │
                     [ 材料提交管理 ] <─────────┤ (血缘关系)
                           │                   │
                           ▼                   │
                     [ 候选人管理 ] <──────────┘ (三阶段漏斗)
                      (自荐/导入)
                           │
                     [ 提案/公告/归档 ] (只读投影)
```

### 主流程与数据流
```
1. [登录]：输入手机号 ── (判角色) ──► 122 村居骨架数据库
2. [新建活动]：母版录入 ──► 选择村/社区 (villages.type) ──► 触发硬规则
3. [自动定岗]：读 villagers.type ──► 匹配法律配置 ──► 一键生成 [主任/副主任/委员] 岗位坑位
4. [村民报名]：提交自荐材料 (materials.scope='candidate') ── (审核通过) ──► 自动生成 [候选人] 并回传
5. [候选人流转]：候选人 ──► [提名] ──► [入围] ──► [正式/竞选] (三阶段漏斗操作)
6. [归档/公告]：母版阶段推进 ──► 阶段对应 N 号公告生成 + 阶段线下会议报告上传 (materials.scope='archive')
```

### 控制流
- 流程完全受**时间节点链 (Timeline)** 约束。
- 系统的状态是“计算出来的”：根据当前系统时间 `now()` 与 `elections.content.timeline` 阶段配置直接判定是否可以报名、是否进入公示、是否进入竞选期。拒绝在各子表维护离散、冗余的状态字段，实现“防呆防错”。

## 【命脉层】- 关键通路

### 依赖链（谁依赖谁）
- 岗位、材料、候选人、公告、历史归档，全部强依赖于 **换届母档案 (elections.id)**。
- 系统的分岔行为（例如生成岗位、校验名额、锁定选举方式），强依赖于 **村居归属地类型 (villages.type)**。
- 权限隔离强依赖于 **用户归属 (users.village_id)** 与 **用户角色 (users.role)**。

### 调用链（怎么调用的）
以“村民材料审核晋升候选人”为例的调用链：
```
[前端页面: 材料提交管理] 点击 [审核通过]
  ──► 发送请求 POST /material-v2/approve { materialId, action: 'approve' }
    ──► Koa 接口拦截：检查 users.role = '审核' 且 material.village_id == user.village_id
      ──► 执行 SQL: UPDATE materials SET status = '通过', reviewer_id = ?
        ──► 触发事务: INSERT INTO candidates (name, phone, position_id, source, election_id) VALUES (...)
          ──► 获取新生成的 candidateId
            ──► 执行 SQL: UPDATE materials SET candidate_id = ? WHERE id = ?
              ──► 返回前端：审核成功，列表局部刷新，候选人管理模块数据同步生成
```

### 数据流（数据怎么流动）
- **材料的三股流向**：
  1. *下载模板类*：平台/超管预置空白模板（`.xlsx`/`.docx` 等） ──► 供小程序端村民**下载**。
  2. *上传存档类*：管理员在母版阶段内上传线下会议留痕报告（`.pdf`/图片） ──► 归入历史归档材料，只供**查看与追溯**。
  3. *用户回传件*：村民手填好模板并盖章后 ──► 拍照/上传回传件 ──► 转化为**自荐候选人材料**，与候选人详情挂钩。

### 决策链（为什么这样做）
- **为什么不碰投票和线上计票？**
  - *法律决策*：依据《村委会组织法》第十一条，村委换届属于国家极其严谨的政治活动，线上投票易受攻击、且无法确保老年选民操作，因此系统坚决不碰线上计票，只做线上报名、材料审核和法定公告公开，线下投完票由运营回填结果。
- **为什么不让子管理自由输入岗位名？**
  - *防错决策*：历史上部分单位胡乱录入“治保主任/妇联主席”，从而引发选票违法。写死为[主任、副主任、委员]，当选后在花名册进行内部分工，在源头上杜绝了数据污染。

### 推理逻辑（当前探索走到哪）
- 当前系统完美实现了母版 B 端的 4 套 9 阶段官方标准套题，具备锁死、拖排、删除、富文本公告及定时发布功能。
- 底座统一引入了 `isdream-vue-admin`。下一步工作是全面对齐子页面在底座中的集成，将原本离散的 HTML 稿，通过统一的“组件小纸条”秒套方式，整合成高性能的 Element Plus 页面，并与 Koa 后端全面对接。

## 【约束层】- 边界条件

### 已确认的重要事实
1. **122个官方村居真名单已灌库**：包含 93 个村委会和 29 个社区居委会，分布于城厢区各个乡镇街道。
2. **种子管理员密码**为 `MD5("123456") = e10adc3949ba59abbe56e057f20f883e`。
3. **法律死线**：村委会的选举方式必须为“全体村民直选”；居委会才允许“户代表、居民代表、直选”三选一。

### 已确认的约束条件
- **一人一岗查重**：村民通过手机号作为身份底座，一人在一届活动里只能报考一个岗位，在材料审核阶段强校验。
- **不可逆流转**：候选人状态一旦进入“最终竞选”阶段，已淘汰和冻结的候选人不允许被逆向召回。
- **只读性**：历史届归档（非当前进行中的活动）全部置为只读，不允许任何上传或删除操作。

### 已排除的方案与原因
- **排除「为超管和子管理开发两套系统」的方案**：开发成本翻倍。最终决策：采用“一套代码，权限过滤，超管UI阉割即子管理UI”。
- **排除「多级复杂部门树配置」的方案**：基层人员用不明白。简化为：直接按 `villages` 平铺表管理，最多按乡镇分组。

### 开放的问题与假设
- **村长的具体 users.role 存储值**：目前临时建议使用 `village_head` 角色。未来是否与 `超级管理` 做更深入的交叉审核，有待进一步跟进。

## 【子管理视角】- 9大页面技术开发明细

### P1. 登录页 (Login)
*实现书香书卷气质、人话文案，隐藏所有开发黑话。*
- **原型参考**：`登录页-美化版.html`
- **底座组件映射 (`isdream-vue-admin`)**：
  - 用 `el-card` 包裹，引入定制红金渐变（`#B22222` 到 `#C8A45C`）的 Head 书香印章背景。
  - 使用 `el-form` + `el-form-item` 绑定。
- **业务需求**：
  - 选择身份：当角色为“超级管理”时，清空并隐藏归属地选择框（超管全区穿透）；当选择“经办/审核/运营”时，必须选择对应的村/社区。
  - 登录后根据返回的 Token 将归属地、用户角色等存入 Pinia/LocalStorage，跳转至工作台。
- **字段插旗 & 后端 API**：
  - 归属地下拉列表必须动态调用 `GET /village-v2/all`。
  - 登录接口：`POST /auth-v2/login`。参数：`{ phone, password, role, villageId }`。

### P2. 首页工作台 (Dashboard)
*作为村社中枢的极简控制台，聚焦日历红条和铃铛通知。*
- **原型参考**：`村长仪表盘-美化版.html`
- **底座组件映射**：
  - 核心日历：`el-calendar`，通过自定义插槽（`#date-cell`）渲染在相应日期范围内的选举事件红条。
  - 统计卡片：`el-row` + `el-col` 布局，采用极简无卡片描边风格。
- **业务需求**：
  - **日历红条驱动**：从 `localStorage.getItem('election_calendar_events')` 或 API 直接读取当前活动的阶段时间轴。在日历中绘制红线条并标明阶段。
  - **右上角消息铃铛**：绑定通知推送模块，点击抽屉展示私信通知。
- **字段插旗 & 后端 API**：
  - `GET /election-v2/current?villageId=xxx` 获取当前活动时间轴与名额。
  - `GET /notification-v2/unread` 拉取当前未读通知。

### P3. 选举活动管理 (Elections - 大母版)
*换届活动的“发源地”和“唯一真相源”。*
- **原型参考**：`页面-活动总列表.html` + `选举系统_填空模板 (1).html` 改造版
- **底座组件映射**：
  - 列表页：`el-table` 展示历届活动。
  - 填空页：采用 `el-steps`（自适应 9 阶段步骤条） + `el-form`（填空表单）。
  - 编辑器：使用 `Vditor` 或基础富文本，用于公告内容的现场即时排版。
- **业务需求**：
  - **四大填空步骤**：建章立制、选民登记、提名、投票选举等。
  - **锁定机制（核心约束）**：资格审查、提名、投票日、选民登记为法律核心关节。提供“锁”图标（禁用删除和名称修改），并悬浮提示“此阶段为法律核心，不可删除”。
  - 支持拖拽、新增其他弹性阶段（如工作移交）。
  - 每一个阶段干 4 件事：编辑填空题、上传空白模板供小程序下载（关联职位材料）、上传线下报告存档留痕、以及定时发布阶段对应的公告。
- **字段插旗 & 后端 API**：
  - `GET/POST/PUT /election-v2`。
  - 时间轴核心字段：`timeline: [ { stageKey, stageName, startAt, endAt, lock, work } ]`。

### P4. 岗位管理 (Positions)
*法定三等，名额和岗位职责在活动上隔离。*
- **原型参考**：`页面-岗位管理.html`
- **底座组件映射**：
  - `el-table` + `el-dialog`。
  - 职位名录名额使用 `el-input-number`。
- **业务需求**：
  - 岗位名固定只允许选择：[主任]、[副主任]、[委员]。**严格禁止自选输入其他非法岗位。**
  - **一键自动生成**：根据当前活动的 `villageScope` 类型（村委会或居委会），点击一键生成时，直接走后端自动生成算法，计算并批量录入标准名额与岗位（如村委直接锁定无副主任或按人数自适应生成 1 主任 2 委员）。
  - **表格材料下载绑定**：在岗位详情弹窗内，可选择关联并引用“材料管理”库中的空白模板（如初步候选人自荐表），一键保存下载地址。
- **字段插旗 & 后端 API**：
  - 生成接口：`POST /position-v2/generate`。参数：`{ electionId, orgType, committeeSize, deputyCount }`。
  - 标准更新：`POST /position-v2/update`（保存职位职责 `duty` 与资质 qualifications）。

### P5. 材料提交管理 (Materials)
*材料的生命史，驱动候选人的产生。*
- **原型参考**：`页面-业务模块.html?module=materials`
- **底座组件映射**：
  - 列表展示：使用 `el-table`，对于逾期提交的材料行，根据母版截止时间自动飘红。
  - 详情预览：`el-dialog`，集成内置 PDF 预览（`iframe`）与大图预览（`v-viewer`），方便盖章回传件的一键极速审查。
- **业务需求**：
  - 分清三类材料：下载模板、上传存档和用户回传自荐材料。
  - **一键审批晋升**：审核人员点击“通过”，将调用接口进行状态更新，并在事务内将该村民一键晋升为“候选人”，自动回填关联 ID 建立闭合血缘。
  - 驳回则弹窗要求必须输入驳回原因，提交后通过通知模块给对应的村民发送短信及内站私信提醒。
- **字段插旗 & 后端 API**：
  - 审核接口：`POST /material-v2/approve`。参数：`{ materialId, action: 'approve' | 'reject', reason }`。

### P6. 候选人管理 (Candidates - 三阶段漏斗)
*高阶审批场景，控制候选人由初选到最终竞选的流变。*
- **原型参考**：`页面-业务模块.html?module=candidates`
- **底座组件映射**：
  - 使用 `el-steps` 或横排 Tab 展示 3 阶段流动漏斗：[提名候选人] ──► [正式候选人] ──► [最终竞选人]。
  - 使用带勾选的 `el-table`，提供淘汰、冻结操作列。
- **业务需求**：
  - **操作自适应**：操作列根据当前母版时间处于哪个阶段而动态变化。例如：在提名公示期提供“移入正式名单”；在正式名单公示期提供“移入最终竞选名单”；任何阶段均可点击“冻结并淘汰”，锁定并不再展示在前端投票页面。
  - 支持“新增候选人”（党组织推荐等线下导入渠道，`source='import'`），支持手机号去重（一人只能报一个岗位）。
- **字段插旗 & 后端 API**：
  - 流转与状态接口：`PUT /candidate-v2/status`。参数：`{ candidateId, status: 'nominated' | 'official' | 'final_contestant' | 'frozen' }`。

### P7. 提案审批 (Proposals)
*降级决策：以弹窗形式快速消化，能不跳页就不跳页。*
- **原型参考**：`页面-提案审批.html`
- **底座组件映射**：
  - 采用极简的 `el-drawer`（抽屉式详情）或 `el-dialog`。
- **业务需求**：
  - 换届期间村民可对未来村居建设提出提案（如：霞皋村自来水改造方案）。
  - 经办对提案进行查看和归类，点击“通过/呈送上级审批/驳回”，完成简单留痕即可。
- **字段插旗 & 后端 API**：
  - 提案在库中与材料表共用同一实体结构，字段为 `materials.scope = 'proposal'`，实现数据层极致复用。
  - `POST /proposal-v2/review`。

### P8. 公告通知 (Notices - 只读投影)
*母版的影子和镜像，只为留痕而生。*
- **原型参考**：`页面-公告通知.html`
- **底座组件映射**：
  - `el-table` 展示公告列表。
- **业务需求**：
  - 不做独立的复杂编辑。公告的内容和发布完全是母版阶段一键填充或定时发布的副产物，本页面仅提供一个一目了然的历届公告只读/预览投影列表，供留痕备查。
- **字段插旗 & 后端 API**：
  - `GET /notice-v2/list?electionId=xxx`。

### P9. 历史归档 (Archives - 目录树)
*大母版阶段推进后的自产果实，零人工分类。*
- **原型参考**：`页面-业务模块.html?module=archives`
- **底座组件映射**：
  - 左侧：`el-tree`（自动计算渲染的阶段树目录：一届选举 ──► 9 个阶段）。
  - 右侧：对应阶段文件夹下已通过的归档文件（`.pdf`、`.xlsx`）平铺列表。
- **业务需求**：
  - 严禁任何人手工对归档文件进行分类，归档树的叶子节点由母版各个阶段的“上传存档类”材料和“审核通过的用户自荐材料”自动流变而成，实现全自动算、归档。
  - 当前进行中的活动允许补传，历届已完成的活动则强制锁死，只读查看，绝不提供删除和上传。
- **字段插旗 & 后端 API**：
  - 接口：`GET /archive-v2/tree?electionId=xxx`（拉取按母版 `timeline` 阶段划分的虚拟目录结构）。

### P10. 后台管理 (Admin settings)
*系统级支撑与资料空白模板存放处。*
- **原型参考**：`页面-后台管理.html`
- **底座组件映射**：
  - 垂直 Tab 分栏布局（`el-tabs tab-position="left"`）。
  - 包含三个子分栏：[基本配置（短信通知/参数）]、[资料库（空白附件上传管理）]、[子管理员名额与账户分配]。
- **业务需求**：
  - **空白资料库（材料血缘源头）**：上传官方 18 种法定文件空白表格（如：初步候选人自荐表），上传后生成的 URL 将作为全局唯一模板，被岗位管理和母版直接引用，避免数据重复存储（“No second truth”）。
  - **子管理账户管理**：村长可以开通并分配“经办”、“运营”、“审核”三个角色，根据名额上限（2/3/2 人）进行控制，超过上限则提示联系平台扩容。
- **字段插旗 & 后端 API**：
  - 附件资料管理接口：`/material-template-v2`。
  - 用户分配与限制：`/user-v2/sub-accounts`。
