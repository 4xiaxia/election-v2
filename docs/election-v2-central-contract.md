## 2. 产品本质

系统是一张按“村居 x 届次 x 阶段 x 岗位 x 人 x 文件用途 x 状态”展开的引导式多维办事账。事实只录一次，公告、表单、审核、结果、花名册和归档全部引用或投影，不重复填报。

两个客户端共享一个后端和一个 MySQL 数据库：

- 管理后台：工作人员办理、审核、发布、确认和归档。
- 选民小程序：公开浏览、下载、自荐、查看本人进度和接收本人站内信。

四个主要工作面：仪表盘、母版、自荐材料审核、候选人审核。简单功能使用独立弹窗/抽屉；母版是允许跳转的核心页面。

## 3. 组织与数据方案（FINAL）

- 一万元基础版只使用一个 MySQL 数据库和一套共享业务表。
- 不按村居动态拼表，不建立每村独立 Database/Schema/服务器。
- 所有村居业务行必须带非空 `organization_id`，服务端强制组织作用域。
- 这是严格组织级逻辑隔离，不是物理隔离；独立数据库/部署属于收费升级服务。
- 所有业务 ID 使用 UUID/ULID；唯一约束和父子关系包含 `organization_id`。
- 文件按组织使用独立私有目录，日志、消息、任务、导出和归档同样带组织字段。
- 从一期保留 `export-organization` 契约，使任一组织未来可完整拔库。

详细字段与导出规则以 `docs/organization-data-and-export-contract.md` 为准。

## 4. 身份与范围

- 唯一身份组合是 `organization_id + normalized_phone`；手机号单独不做全系统唯一。
- 后台导入候选人与前端认领的归属地、规范化手机号必须两项完全一致；任一项不同就不认，不按姓名猜。
- 用户首次选择归属地后不提供自助改绑。选错归属地由客服执行数据库级迁移并留痕，属于额外收费服务。
- 本期不接短信验证码，不能宣传为强实名；敏感原件权限冻结前不得仅凭弱认领开放。
- 业务表引用稳定 `accounts.id`，不用手机号字符串充当跨模块外键。后台导入可先创建 `claim_status=unclaimed` 账号，前端精确匹配后更新为 `claimed`，业务 ID 不变。
- 普通账号只访问所属组织。客户端 `organization_id`、角色、筛选器或 readonly 标记都不能授权。
- 基础版接受“归属地 + 手机号”无法证明手机号持有权的风险；站内信不得承载身份证原件、私人附件或完整资格材料。验证码、实名或其他强化认领属于后续安全升级。

## 5. 角色临时基线

- `sub_admin` 严格限制在自己的村/社区。
- `sub_admin` 只有审核相关业务可写，所有非审核业务只读；人员管理也只读。
- “审核相关”必须在 RBAC 实现前变成稳定 action key 白名单；未知动作默认拒绝。
- `super_admin` 先看全部村/社区列表，点击详情后取得绑定该组织的短期签名 scope/token；每个请求显式携带，避免多标签页串村。
- `super_admin` 进入组织后至少具备 `sub_admin` 能力，并可创建/分配角色、配置每角色可绑定数量。其他写权限仍须 action key 明确授权和审计。

## 6. 业务硬规则

1. HTML 是 2.0 产品规格；1.0 只打捞认证、权限、上传、富文本、表格、导入导出和事务等技术资产。
2. 提案批准原子、幂等地创建并绑定唯一 `electionId`；不存在第二个创建活动入口。
3. 一期岗位只有主任、副主任、委员；选举方式属于整届，不属于岗位或候选来源。
4. 村/社区共用一套八阶段骨架，差异进入组织术语和 election method profile。
5. 母版实际日期由甲方填写；已有下游事实时改期必须影响预览、版本校验、原因、任务重排和审计。
6. 材料管理只负责一人一岗的一份完整私人自荐申请，不负责母版附件或综合归档。
7. 自荐材料收审检查选民关系、一人一岗和材料完整性，不是候选资格审核。
8. 自荐、联名提名和党组织推荐汇入同一候选池；同届同人合并、保留多来源，岗位冲突解决前不得继续。
9. 三轮资格审核全部发生在第 3 阶段；阶段 4 只公示正式候选人并处理异议；预选不是第四轮审核。
10. 公告是组织对公众；站内信是对手机号绑定账号。选民和管理员可收本人消息，游客不收；后台待办只发有权限的工作人员。
11. 公共下载模板、正式公告、内部档案证据和私人自荐原件是不同用途与权限。
12. 一届一个归档根；文件对象、业务引用和归档目录项分层，不因归档复制字节。
13. 花名册不是管理员表。初始可手工录入；最终中选人只生成刷新预览，由甲方确认后保存历届快照。
14. 提案草稿可编辑；提交后锁定；驳回保留被驳回快照并创建可编辑新版本；批准后永久只读。首页和列表打开同一提案弹窗，不复制状态机。
15. 岗位是每届前置根骨：稳定 `positionId`、岗位类型、计划当选数、说明和自荐模板被母版、申请、候选、结果和花名册复用；产生下游事实后禁止破坏性删除或换 ID。
16. 花名册按“任期 + 岗位 + 人”保存独立 roster entry，支持一岗多人、树状展示、人物简介/资历/事迹和历届筛选。刷新先展示新旧差异，人工确认后生成新届只读快照，不覆盖旧任期。

## 7. 唯一纵向目标链

```text
提案提交/审核
  -> 批准并生成唯一 electionId
  -> 母版八阶段实际时间
  -> 主任/副主任/委员配置
  -> 小程序一人一岗自荐
  -> 材料收审
  -> 多来源候选池
  -> 第3阶段三轮资格审核
  -> 第4阶段正式候选人公示
  -> D日结果录入与确认
  -> 17号公告草稿
  -> 花名册刷新预览与人工确认
  -> 本届归档
  -> 历史只读
```

任何页面只是该链的入口或投影，不能再造第二套业务真相。

## 9. 工程门

- 提案批准命令必须冻结输入快照、模板版本、返回值、回滚和附件引用。
- 跨聚合交易由 application command/orchestrator 在同一组织和事务中编排。
- RBAC 使用稳定 action keys，未知动作默认拒绝；`primaryRole` 不参与授权判断。
- 生产法律强校验必须挂接适用正式法源/地方文件及版本；咨询、Excel 和模板不能单独授权自动裁决。
- 保存、刷新、重登、重试、组织越权、历史只读、文件权限和审计必须进入端到端验收。
- 超管/系统审计使用 `actor_type + actor_id + actor_name_snapshot`，不得强制外键到组织账号；组织导出后仍能读懂平台操作证据。
- 组织独立导出必须使用专用 action key、双人审批、加密包、短时下载和完整审计；`P0-PRIVACY` 未冻结前不得实现真实全量导出。

## 10. 商业边界

- 一万元基础版：一个后端、一个管理后台、一个选民小程序、一个共享数据库、约定组织/账号/部署范围。
- 不包含每村独立表/数据库/服务器、无限账号、长期内容维护、长期运维、外部对象存储或真实短信费用。
- 初始约定范围外的新增组织、账号额度、政策适配、版本升级、独立拔库/部署、文件与数据迁移、人工纠错均走变更单收费。
- 质保期内属于本次验收范围的程序缺陷免费修复；不能把交付缺陷包装成收费升级。
